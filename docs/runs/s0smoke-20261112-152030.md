## Problems / observations
1. **The trainer, not the games, is again the bottleneck, and 3× slower per update than in Spike A.**
   - `PPO train` takes 11.2 s per batch, against 2.2 s for the reach task.
   - The combat policy has a 128-wide memory state trained over 16-step windows (`PolicyWindow 16`, 1,024 windows per policy minibatch) and attention encoders for the enemy and sound sets (saved config).
   - GPU use stays at 6–8%, so the cost is per-step overhead, not the GPU's capacity. Spike B on combat (L-007 (2)) measures this per N × K.
2. **Log volume is small so far.**
   - Each game log is 76 KB for 3 batches.
   - `Resetting Agents [0 … 15]` appears once per 20 s of game time (12–19 lines per game). The untrained agents all time out together, so all 16 arenas reset in one call.
   - Once agents clear at different times, expect up to one such line per decision step; S0 training watches this.
   - The game's stdout repeats the log line for line (76 KB too). `combat.sbatch` discards it by default (`GAME_STDOUT=0`).
3. **`CombatStats` windows alternate between 16 and 0 episodes** while all arenas time out in step: 20 s episodes against a 10 s window. This is expected and not a bug.
4. **The trainer prints `Exception in thread ... (_worker)` tracebacks at shutdown** (`_test_connection`, after `Socket Communicator Exiting...`).
   - They appear only with the shortened polls. All 6 `:poll` configs of Spike B job 151931 show them; none of the stock configs do.
   - They come after training has completed, the games have exited 0 and the trainer exits 0.
   - They are cosmetic: the `_worker` threads now wake within 10 ms and touch sockets the games just closed. Heartbeats and timeouts are not affected. No action needed, so the patch stays (D-029).
5. Engine startup is quick on this build: about 3 s from launch to `Combat: ready`, and the 20-episode eval took 7 s in total.
